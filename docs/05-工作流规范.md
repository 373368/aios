# 工作流规范（v1）

> 定位：定义 AI-OS 中"工作流 = 特定场景多原语编排"的统一入口契约与触发层约定。让新工作流照此扩展，触发方式可拔插。
> 依据：2026-08-17 决策「工作流触发方式解耦」(`04-决策记录/2026-08-17-工作流触发方式解耦.md`)、2026-08-22 运行治理统一（三层模型）。
> 原则：**工作流 = 逻辑组件（载体自选），是原语（工具统一体）的多调用编排 + 锁/日志/退出码；触发 = 外部层（任何能调用入口的机制）；SDK = LLM 参与的整合监控层，驱动并管理工作流。**

## 1. 工作流入口契约

每个工作流必须暴露**一个统一可执行入口**，触发器只认这个入口，不关心内部实现。

```
入口（任选，宿主无关）：
  ps1 脚本      → powershell -File <workflow>.ps1
  python 脚本   → python <workflow>.py
  node 脚本     → node <workflow>.js
  opencode run  → opencode run --command <cmd>   # LLM 提炼/判断环节
  YAML 声明式  → python l2-memory\workflows\wfengine.py <workflow.yaml> [k=v]   # 声明式三层（推荐，见 §6）

统一约束：
  1. 单一入口：一个工作流 = 一个入口命令（编排壳可内部调多脚本）
  2. 退出码约定：0=成功  非0=失败（触发器据此判断）
  3. 单实例锁：并发重入时直接退出（防多触发器同时触发）
  4. 日志：写自身 run 日志 + 可追加到全局日志
```

## 2. 元数据（工作流自述）

每个工作流目录放一份 `workflow.json`（或代码注释等价物），供触发器/人发现：

```json
{
  "name": "auto-archive",
  "description": "网页 AI 对话导出→提炼→索引→行为记录",
  "entry": "powershell -File <repo>/l2-memory\\tasks\\auto-archive.ps1",
  "trigger": ["manual", "schedule"],
  "log": "<vault>/03-日志\\archive-auto.log",
  "depends": ["export-doubao", "export-yuanbao", "deepseek_split", "scan_new", "opencode-run"]
}
```

字段：
- `name`/`description`：标识与用途
- `entry`：可执行入口（触发器调这个）
- `trigger`：声明支持的触发方式（`manual`/`schedule`/`event`/`program`）——**声明而非实现**，具体由外部触发器匹配
- `log`：运行日志位置
- `depends`：依赖的脚本/组件（人读，不强制解析）

## 3. 触发层约定

触发层 = 独立组件，**只负责"何时调 + 调谁"**，不编码进工作流。

| 触发方式 | 实现载体 | 状态 |
|---|---|---|
| manual | 手动命令 / `opencode run --command` | ✅ 现有 |
| schedule | Windows 计划任务（schtasks，已停用可重开） | 🔌 可重开 |
| event | 文件监听 / 其它程序回调 | 🔌 预留 |
| program | 另一程序直接调入口 | 🔌 预留 |

触发层实现规则：
1. 触发器只调 `workflow.json` 的 `entry`，不解析工作流内部
2. 触发器必须处理退出码（0/非0）并记录触发结果
3. 并发防护由工作流自身单实例锁承担，触发器不重复实现

## 4. 工作流 vs 触发器的边界（决策回顾）

| 层次 | 职责 | 示例 |
|---|---|---|
| 工作流本体 | 完成任务的逻辑，纯组件无定时逻辑 | auto-archive.ps1 |
| 触发层 | 决定何时调用工作流入口 | 计划任务 / 事件监听 / 手动 |

## 6. 声明式工作流（YAML + wfengine，推荐形态）

工作流本体以 YAML 声明（对齐微软 Agent Framework Declarative Workflows 1.0），由 `l2-memory/workflows/wfengine.py` 执行：

- **结构**：`kind: Workflow` + `metadata` + `trigger` + `variables` + `actions`（InvokePrimitive / InvokeLLM / ConditionGroup / Loop / SetVariable，动作可带 `when`）
- **表达式**：`=` 前缀（=System.Args.x / =Local.x / =Loop.Item / 比较运算），`{var}` 内嵌替换
- **判断点**：prompt 模板存 `workflows/prompts/*_judge.txt`，输出严格 JSON 含 `branch`，由 ConditionGroup 路由
- **执行**：`python workflows\wfengine.py <workflow.yaml> [k=v]`（退出码 0/非0，日志 `03-日志/wfengine.log`）
- **可拔插**：参数/判据走 CLI args + prompt 模板 + 原语 args，不写死在引擎

载体选型：新工作流默认 YAML 声明式；ps1/py 编排壳仅在「需要原生进程控制（细粒度锁/平台 API）」时保留。完整使用规范见 `declarative-workflows` skill。

## 7. 演进原则（ponytail）

- **只有 1 个工作流时**：不建注册框架/统一触发器，入口契约 + workflow.json 足够
- **第 2 个工作流出现时**：才考虑通用 `trigger.ps1` 按 metadata 分发
- 载体不强制：ps1/py/js 谁顺手用谁，入口契约是唯一硬约定
