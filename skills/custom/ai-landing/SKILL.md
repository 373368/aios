# AI Landing — 通用 AI 落地方法论

> 源自 **Palantir FDE（Forward Deployed Engineer）× AIP（AI Platform）** 范式，去掉了 Palantir 专属产品细节，提炼成可在任何项目复用的落地方法论。核心一句话：**先在真实现场搞清楚要解决什么，再用真实数据小步验证 AI 能不能行，最后把验证通过的方案受控地接进真实流程。**

## 定位与适用

**适用**：在真实业务/系统里落地 AI 的场景——规划 AI 功能、把 AI 接进现有流程、决定"这个 AI 想法怎么做成能用的东西"。包括个人系统（如 AI-OS）、企业项目、从零到一的项目。

**不适用**：纯算法研究、纯学术探索、已有明确需求且一步到位的简单脚本（这类直接用，不需要方法论）。

**三种模式**（按场景选择）：
1. **落地路线图**：产出一份结构化落地文档（现状审计→验证计划→部署步骤→风险）。
2. **对话式引导**：把方法论当框架，按阶段逐步问诊+推进，不强制一次性产出文档。
3. **两者结合**（默认）：框架 + 关键节点产出结构化文档。

## 核心思想

1. **现场优先（Forward Deployed）**：先到真实场景里搞清楚"到底要解决什么问题"，不是从技术方案出发。技术可行性 ↔ 业务优先级要**同步双轨判断**，而不是单向推演。
2. **数据先行，小步验证**：用真实数据快速验证 AI 能不能行、行到什么程度——避免大规模构建后才发现问题。
3. **人在回路（Human-in-the-Loop）**：关键决策点保留人的判断，AI 只辅助不替代。
4. **受控执行（Controlled Execution）**：AI 落地不是"让 AI 自由发挥"，而是"LLM 只申请、业务系统是事实源、每次执行有审计"。
5. **语义层是地基（Ontology 式建模）**：数据之上加一层"语义 + 行动 + 治理"的受控操作层，而不是堆裸数据/裸接口。

## 方法论框架：三阶段 + 语义层

```
Audit（审计/理解）
  └─ 在真实现场搞清：业务问题 / 数据在哪 / 决策链怎么走
       ↓
Evals（评估/验证）
  └─ 用真实数据快速验证：AI 能不能解决 / 解决到什么程度
       ↓
Deployment（部署/落地）
  └─ 把验证通过的方案受控接进真实流程（语义层 + 行动层 + 审计）
```

### 阶段一：Audit（审计/理解）

目标：**准确画像"这个组织/系统到底要解决什么"**，而非直接动手。

- [ ] 识别真实业务问题（不是用户口述的"想要个 AI"，而是背后的痛点）
- [ ] 盘点现有数据资产：数据在哪、什么格式、质量如何
- [ ] 理清决策链：谁做决定、基于什么信息、流程怎么走
- [ ] 评估技术可行性 ↔ 业务优先级的匹配度（双轨）

**产出**：问题画像 + 数据清单 + 决策链描述 + 可行性初判。

### 阶段二：Evals（评估/验证）

目标：**用真实数据证明"AI 能解决到什么程度"**。

- [ ] 用真实数据（不是理想化样例）构造验证集
- [ ] 定评估指标（与业务目标对齐，不追求学术指标）
- [ ] 小步跑通一个最小闭环，记录成功率/失败模式
- [ ] 判断：可行 → 进部署；部分可行 → 调整范围；不可行 → 诚实止损

**关键**：Evals 的价值在于**在大量构建前暴露方向错误**。验证不过就调整/止损，不硬撑。

**产出**：验证结果 + 成功率/失败模式 + 是否进入部署的明确判断。

### 阶段三：Deployment（部署/落地）

目标：**把验证通过的方案安全地接进真实流程**。

- [ ] 定义语义层（见下）——把领域实体、关系、可执行操作建模出来
- [ ] 受控执行三原则：
  1. **LLM 只申请（propose）**：AI 提出动作，不直接执行
  2. **业务系统是事实源（source of truth）**：以真实系统状态为准
  3. **每次执行有审计（audit）**：记录谁在何时做了什么
- [ ] 人在回路：关键动作保留确认/审批
- [ ] 回滚预案：出问题能退回上一步
- [ ] 上线后监控 + 迭代

**产出**：部署方案 + 语义层模型 + 受控执行规则 + 回滚预案。

## Ontology 式语义建模（Deployment 阶段的核心）

普通数据层描述"世界是什么"；**语义层额外描述"世界怎么被改变 + 谁有权改变"**。建模时定义两类元素：

| 元素 | 定义 | 对应问题 |
|---|---|---|
| **语义元素** | objects（对象）/ properties（属性）/ links（关系） | 世界"是什么" |
| **动能元素** | action types（可执行动作）/ functions（业务逻辑）/ 动态安全 | 世界"怎么被改变"+"谁有权" |

建模要点：
- 把数据源映射成**有关系的实体**（不是一堆孤立的表）
- 每个实体定义可对其执行的操作（受治理约束）
- 操作背后可挂业务逻辑（任意复杂度）
- 权限/审计内建于模型，不是事后补

> **类比**：就像 OS 的"地址空间"——数据是内存，语义层是"寻址 + 保护 + 执行权限"，让上层 AI 能安全地读写真实世界。

## 常见失败模式（避坑）

1. **数据质量悬崖**：看着数据齐全，一接入真实系统发现脏数据/缺字段。
2. **治理债**：上线时没定权限/审计，后续补比一开始定贵得多。
3. **成功的反噬**：第一个场景成功后，盲目扩展到不合适的第二个场景。
4. **第二场景失效**：第一个场景的定制方案硬套到别的场景。
5. **模型漂移**：上线后不监控，数据分布变了模型悄悄失效。

## 落地工作流（默认推荐路径）

当触发本 skill 时，默认按以下流程走（对话式引导 + 关键节点产出文档）：

1. **Ask 入口问题**（判断场景）：
   - 要解决什么真实问题？
   - 数据在哪、什么形态？
   - 决策链/流程怎么走？
   - 期望的产出形式（路线图/对话式/两者）？
2. **阶段一 Audit** → 产出问题画像（短文档或对话小结）
3. **阶段二 Evals** → 产出验证计划 + 跑通最小闭环
4. **阶段三 Deployment** → 产出部署方案 + 语义层模型 + 受控执行规则
5. **收尾**：避坑清单检查 + 监控/迭代安排

当用户要"落地路线图"文档时，用此结构：

```
# <项目名> AI 落地路线图

  - 真实问题 / 数据资产 / 决策链 / 可行性初判
## 二、验证计划（Evals）
  - 验证集 / 评估指标 / 最小闭环 / 成功标准

  - 数据质量 / 治理 / 反噬 / 第二场景 / 漂移
## 五、迭代与监控
```

## 与常见概念的关系

- **与 RAG 的区别**：RAG 是检索技术，本方法论是"决定要不要用、怎么落地 AI"的框架。RAG 可能出现在本方法的 Evals/Deployment 阶段，但不是它本身。
- **与"AI Agent"的关系**：Agent 是执行形态，本方法论决定"该不该建 agent、建了怎么受控落地"。
- **与 Palantir 的区分**：Palantir 是企业级产品（Foundry/Ontology/AIP），本 skill 取其方法论（现场优先 + 语义层 + 受控执行 + 小步验证），去掉产品依赖，可套用到个人/开源/国产化任何栈。
