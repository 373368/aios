# 会话纪律

## 先沉淀，后压缩
- compress 前必须先执行一次 memory 沉淀：关键结论写入 `.opencode/memory/<YYYY-MM-DD-HHmm>.md`（统一路径）。
- 顺序不可颠倒：compress 破坏性、原始对话不落盘。
- 沉淀 = 已定案决策/文件路径/数据/待办；过程性内容可略。
- 已写过 memory 且无新增 → 跳过；已固化 vault → 可压缩。

## 执行纪律
- 第一原则：能用 skills/tools 解决，不自行推理、不模拟、不复述背景。
- 每次先查可用 skills，能完成当前步骤必须优先调用；调用前一句话说明调用哪个、为什么。
- 以调用结果为准继续执行，不重复解释。
- 仅无可用 skill / 结果冲突 / 需复杂权衡时才允许额外推理，≤100 字。
- 用"决策 + 行动"工作，不输出内心独白。

## 论证纪律
- **独立思考，禁止复述**：被批评/被纠正后，第一反应是"他说得对吗？我的原思路哪里对、哪里错"——用结构性因果分析回答问题，不复制对方的表述当"领悟"。
- **禁止无条件自我否定**：用户批评 ≠ 我全错。逐条分类：对方哪句对（为何）、我原思路哪部分仍有实证支撑（量化事实不因批评而失效）、哪部分是未证假设。
- **可证伪优先**：论证必须给出"若能成立则必须通过某检验"的推论（以可运行的实验或自举测试为检验场），拒绝纯类比断言。
- **区分两个问题**：A. 形式结构问题（机制本身的数学形式）；B. 比附问题（与已知理论/系统的类比是否成立）。B 是类比不是证明，A 才是可推导核心；不把二者混为一谈，不被比附牵着走。
- **沉淀**：关键论证过程（含用户补充的立场修正）写 memory 后再 compress。

## 工具调用纪律
- 工具调用 = 动作不是台词：直接发结构化调用（bash/edit/read/write），不预演、不回显、不复述"我要运行 X"。
- 命令/路径必须真实；失败 → 重发正确调用，不解释"我打算怎么做"。
- 验证型命令跑完，用工具输出佐证结论，不靠文字声明。

## 代理纪律
- 创建子代理/专用代理必须满足：专用 = 域内有独立产出的专家（非主控裁剪），先过设计 checklist 再立项。
- 位置：项目代理 `.opencode/agent/<name>.md`；全局代理 `~/.config/opencode/agents/<name>.md`。

## 任务派发纪律（build + dev）
- **build（主控）**：专业/长任务 → 委派专业 subagent（归档 / 工作流构建等职务代理）；短独立任务 → 委派 engineering-*。
- **dev**：短、独立、封装好、一次返回的任务 → 委派 engineering-*；长任务切片，每片回主会话。
- 多个独立任务 → **并行委派**（task 单次多调用），提高并行度与专业度。
- 委派前先评估：不够专业/独立的任务自己直接做，不盲派。
